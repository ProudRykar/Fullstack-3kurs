# Тестовая модель приложения

## 1. Критические пользовательские сценарии

| # | Сценарий | Роль | Описание |
|---|----------|------|----------|
| 1 | Регистрация нового пользователя | guest | Заполнение формы → валидация → создание пользователя → редирект на логин |
| 2 | Вход в систему | guest | Ввод identifier/password → создание сессии → установка cookie → редирект |
| 3 | Выход из системы | user/admin | Нажатие кнопки "Выйти" → сброс сессии → редирект на /login |
| 4 | Просмотр товаров | user/admin | GET /products → отображение списка с пагинацией |
| 5 | Создание товара | admin | POST /products → валидация → сохранение → отображение в списке |
| 6 | Редактирование товара | admin | PUT /products/{id} → обновление полей → отображение изменений |
| 7 | Удаление товара | admin | DELETE /products/{id} → подтверждение → удаление → обновление списка |
| 8 | Приёмка товара | user/admin | Создание накладной → добавление позиций → подтверждение → списание ячеек |
| 9 | Инвентаризация | user/admin | Создание сессии → сканирование товаров → завершение → отчёт |
| 10 | Управление складами | user/admin | CRUD складов + управление ячейками + размещение товаров |
| 11 | Загрузка изображения | user/admin | POST /users/upload_image → сохранение в MinIO → отображение |
| 12 | Администрирование: список пользователей | admin | GET /admin/users → просмотр всех пользователей |
| 13 | Администрирование: смена роли | admin | PATCH /admin/users/{id}/role → обновление роли |

## 2. Ключевые бизнес-правила и ограничения

### Аутентификация и сессии
- Пароль: минимум 8 символов, требуется цифра, заглавная, строчная, спецсимвол
- Username: 3-20 символов, только латиница, цифры, `_`, `-`
- Email: проверка формата, max 254 символа
- Access token: 15 минут, Refresh token: 7 дней
- Refresh token хранится в httpOnly cookie
- После смены пароля все сессии сбрасываются
- Нельзя повторно использовать refresh token (blacklist)

### Роли и права доступа
| Роль | Разрешённые операции |
|------|----------------------|
| guest | Нет доступа к API (кроме health/auth) |
| user | Просмотр/создание товаров, приёмка, инвентаризация, склады, загрузка изображений |
| admin | Всё, что user + удаление товаров, управление пользователями и ролями |

### Товары
- SKU и barcode должны быть уникальны (в пределах БД)
- При создании товара без SKU генерируется автоматически
- При редактировании товара обновляется updated_at
- Удаление товара каскадно не удаляет связанные сущности

### Приёмка (Receipts)
- Статусы: draft → confirmed / cancelled
- Нельзя подтвердить пустую накладную
- Нельзя изменить подтверждённую/отменённую накладную
- При подтверждении товар размещается в ячейках склада

### Инвентаризация
- Статусы: active → completed
- Активная сессия только одна на склад
- Нельзя завершить неактивную сессию
- Сканирование учитывает quantity

### Склады и ячейки
- При создании склада генерируются ячейки (A1..Z100)
- Ячейка имеет вместимость (capacity)
- Размещение товара в ячейке проверяет свободное место
- При удалении склада удаляются и ячейки

### Изображения
- Допустимые расширения: png, jpg, jpeg, gif
- Размер файла: до 10MB
- Изображения хранятся в MinIO (S3-совместимое хранилище)
- Пользователь видит только свои изображения

## 3. Области повышенного риска

| Область | Риск | Меры |
|---------|------|------|
| **Аутентификация** | Подбор пароля, кража токена, XSS/CSRF | HttpOnly cookie, rate limiting, blacklist токенов |
| **Роли/права** | Повышение привилегий, неавторизованный доступ | RBAC на каждом endpoint, фронтенд-гарды |
| **Работа с файлами** | Загрузка вредоносных файлов, превышение лимитов | Валидация типа/размера, хранение в S3 с presigned URLs |
| **Интеграции API** | Отказ MinIO/Redis/MongoDB, таймауты | Graceful degradation, health checks, error handlers |
| **Безопасность данных** | SQL injection (NoSQL injection), утечка данных | Параметризованные запросы, изоляция tenant'ов |

## 4. Уровни тестирования

| Уровень | Инструмент | Что покрывает | Маркер/суффикс |
|---------|-----------|---------------|----------------|
| Модульные (Unit) | pytest, vitest | Модели, DTO, сервисы, утилиты, валидаторы | pytest: `unit` |
| Интеграционные | TestClient, RTL | Роутеры, шлюзы, контексты, компоненты с API | pytest: `integration` |
| Сквозные (E2E) | TestClient (full app) | Полные бизнес-сценарии (auth → CRUD → logout) | pytest: `e2e` |

## 5. Структура тестов

```
tests/                          # Backend
  conftest.py                   # Глобальные фикстуры и моки
  test_domain_models.py         # Unit: модели предметной области
  test_product_dto.py           # Unit: DTO
  test_rbac_service.py          # Unit: RBAC
  test_*_service.py             # Unit: сервисы
  test_*_gateway.py             # Unit: шлюзы (Mongo, Redis, MinIO)
  test_*_router.py              # Integration: endpoints
  test_error_codes.py           # Unit: коды ошибок
  test_problem_handlers.py      # Unit: обработчики ошибок
  test_e2e_scenarios.py         # E2E: полные бизнес-сценарии

frontend/src/test/              # Frontend
  setup.ts                      # Настройка jsdom
  utils/permissions.test.ts     # Unit: утилиты
  services/api.test.ts          # Unit: API-клиент
  context/*.test.tsx            # Integration: контексты
  components/*.test.tsx         # Integration: компоненты
  pages/*.test.tsx              # Integration: страницы
```

## 6. Метрики качества

| Метрика | Цель |
|---------|------|
| Покрытие backend (statement) | ≥ 70% |
| Покрытие frontend (statement) | ≥ 50% |
| Unit-тестов | ≥ 70% от общего числа |
| Пропорция unit/integration/e2e | 70/20/10 |
| Все тесты проходят | 100% перед merge |
